# Praksis: Concept Summary and Project Plan

## Context

The goal is to replace the "one program per function" model of local software with one general local system. Modules provide capabilities, and rulesets define what the software actually does. Nothing is built yet (the repo is empty and clean), so this plan records the ideas gathered so far, lists the open questions, and proposes a sequence for design and implementation. It is a starting point to refine, not a final design.

## Core Concept

- **Capabilities** (what we are able to do) are the union of everything the installed modules provide. Modules may be composed into higher-level capabilities.
- **Policies** (what we are willing to do and have to) are expressed as rulesets. Rulesets are the only layer that calls modules.
- Capabilities being available does not mean they run. Rulesets decide what is used, when and under which conditions.

## Components Gathered So Far

1. **Modules**: plugins that provide capabilities, including access to external storage (S3, WebDAV, IMAP, ...).
2. **Rulesets**: define actions, with access to modules.
   - Hosted in git repos, so versioned and auditable.
   - Cascadable: a public upstream ruleset plus a private local layer (e.g. "use the public mail processing ruleset plus one extra rule of mine").
3. **Triggers**: user initiation, scheduler events, external events.
4. **Backend (engine)**: runs the rulesets, ideally on the same machine, ideally with a GUI. Apache NiFi was considered and rejected as the runtime (see Decisions).
5. **Frontend**: desktop app for all major OSes, starting with Linux. JavaFX is preferred.
6. **Local storage**: simple to maintain but flexible, with the same interface for local and external storage.
7. **Configuration store**: configuration, access control, credential management.

## Observations and Leanings (not decisions)

- **Frontend**: JavaFX fits (cross-platform, JGit, Java module system). Running the engine as its own local process makes the frontend one client among several and lets scheduled and external events run with no window open.
- **NiFi**: good for modules/processors, scheduling, GUI and provenance, but it is a dataflow tool, not a ruleset engine. It has no native layering of flows, is heavy for a desktop, and gives limited control over permissions for foreign rulesets. A lighter custom engine, with NiFi as an option or a reference, may fit better.
- **Storage**: SQLite for engine state (events, history, settings), files plus an index for user data, behind a common storage interface.
- **Credentials**: stored separately from rulesets. Rulesets reference credentials by name only. Use OS-native secret stores (libsecret, Keychain, Credential Manager) or an encrypted vault.
- **Trust**: public rulesets are untrusted input. Each ruleset is granted only specific capabilities and credentials.

## Decisions

### Cascading semantics
- Every rule has a **stable ID**.
- A ruleset is an **ordered stack of layers**, applied bottom to top (no multiple inheritance, so no diamond problems).
- A layer's operations are `add`, `replace`, `disable` and `patch` (change a single field of an upstream rule). A target that is missing or has changed is a visible error, never a silent skip.
- Upstream rulesets are **pinned** to a commit or tag in a lockfile. Updates are explicit.
- The engine offers an **effective view**: the merged result, with the layer each rule comes from.
- **Permissions are not overridable by rulesets.** Grants for capabilities and credentials stay local.
- Extension points that upstream authors declare may be added later as an optional feature.

### Rule execution
- **All matching rules fire**, ordered by layer position, then declaration order. There are no numeric priorities. Phases are deferred: plain ordering is enough for the first version.
- `stop` is an explicit action, so first-match behavior is available where wanted.
- **Conflicting effects** on the same target are an error. The verifier detects them statically where it can, and the engine catches them at runtime.
- Rules may **emit events**, with a depth limit and loop detection. There is no fixpoint (forward) chaining.
- Every event has an **idempotency key**, so reprocessing an event does nothing twice.
- Events are processed **one at a time per target** and in parallel across different targets.
- On failure the engine records it and continues with the other rules, unless the rule is marked as required. Retry and compensation are deferred.
- The same event and the same ruleset always produce the same actions in the same order, which keeps replay and shadow mode meaningful.

### Ruleset format
- **TOML** files with a published schema, **one file per rule**, named by its stable ID. Actions are written as arrays of tables (`[[action]]`) to keep nesting manageable.
- **Conditions and value expressions are written in CEL** (Common Expression Language): sandboxed, side-effect-free, always terminating, with an official Java implementation.
- **Actions are structured calls** to named module capabilities with typed parameters, never free-form code.
- Each rule declares its **effect classification** and the **capabilities and credentials** it needs, so the verifier can check them and compute the permission diff.
- Every ruleset carries a **format version**, so an engine can reject rulesets it cannot run.
- Rejected: a custom DSL (grammar and tooling cost, harder to layer, less reliable for an AI), embedded general-purpose scripting (not verifiable, code execution for public rulesets), and an existing rules engine's native format (ties the project to its execution model).

### Triggers and data model
- **One typed event bus.** Everything is an event: schedule ticks, user commands and events from modules (e.g. `mail.received`). Rules subscribe by event type with an optional CEL filter.
- **Event envelope** (CloudEvents-like): `id`, `type`, `source`, `time`, `target`, `key` (idempotency), `parent` and `depth` (for emitted events) and a `data` payload. The `target` drives the per-target serialization.
- **Hybrid data model.** The envelope and the core fields of each event type are typed through the declaring module's metadata. A free-form `data` map holds module-specific extras. The verifier type-checks CEL expressions and action arguments against the typed parts.
- **Triggers** live in a `[trigger]` section with one `kind`:
  - `event`: `type` plus an optional CEL `filter`.
  - `schedule`: `cron`, `timezone` and `catch_up = "skip" | "once"` (default `skip`) for runs missed while the daemon was down.
  - `command`: a name, a title and typed parameters, so a frontend can generate forms.
- **External event sources** (IMAP idle, file watcher, webhook endpoint via Camel) are provided by modules. Listening is itself a capability and needs a grant.
- **Actions** are `[[action]]` tables with an `id`, a `capability` and `args`. Each argument is a literal or an explicit expression, `{ cel = "..." }`, so there is no string-templating ambiguity.
- **CEL variables:** `event`, `results.<action_id>` (outputs of earlier actions in the same rule), `params` (ruleset parameters) and `now`.
- **Ruleset parameters:** a ruleset declares named parameters with defaults, and a layer can set them without patching rules.
- Rules communicate only through emitted events. There is no shared mutable state in the engine, and persistence goes through a storage capability. **No per-rule persistent state in the first version.**
- Not chosen: separate trigger kinds with separate semantics, and state reconciliation (polling against a desired state) as the core model.

Example rule:
```toml
id = "mail.archive-newsletters"
effect = "local-write"
needs = ["mail.move"]

[trigger]
kind = "event"
type = "mail.received"
filter = "event.data.headers['List-Id'] != ''"

[[action]]
id = "move"
capability = "mail.move"
args = { message = { cel = "event.data.message" }, folder = { cel = "params.newsletter_folder" } }
```

### Engine
- A **custom engine in Java, running as a daemon** (a separate local process), so scheduled and external events work with no window open. Frontends, including a CLI, connect through a local API.
- **Apache Camel** is used inside modules where it saves work (connectors for IMAP, S3, WebDAV, files and more). It is not the engine.
- The engine core stays **free of JavaFX and other UI dependencies**, so the runtime could be changed later.
- Events are **persisted in SQLite**, so a crash does not lose them.
- Packaging with a bundled runtime per OS (`jlink` and `jpackage`).
- Rejected: Apache NiFi as the runtime (its flow-graph model does not map onto flat rule ordering, layering and per-target serialization, and it is heavy for a desktop), a Go or Rust engine (Java preferred, one language with the frontend), and existing workflow engines such as Node-RED, n8n, Temporal and Camunda (they impose their own models). NiFi may still be added later as a module for heavy data jobs.
- The risks were checked in the **M0 spike** (verdict: go, see `spikes/m0/FINDINGS.md`): cel-java type-checks events whose types are built at runtime as protobuf descriptors, and a `jlink` image with a Camel layer used about 100 MB of memory and 0.8 s for a short run. cel-java is still 0.x, so pin its version and keep it behind our own expression interface. The footprint of the real engine was re-measured at M1: about 150 MB idle and 200 MB after real work, see "Footprint, measured at M1".

### Module system
- **JPMS** (the Java module system). A `capability-api` module holds the capability interfaces and metadata types. Modules implement them with `provides ... with`, and the engine finds them through `ServiceLoader`.
- Modules are loaded from a modules directory at startup into **their own `ModuleLayer`**. There is no unload, so removing a module takes a restart.
- If Camel causes JPMS problems (automatic modules, split packages), its jars are **encapsulated inside our own JPMS modules**, and only our own service interfaces expose the capability. Rulesets and the engine never see Camel types.
- Each capability's **name, typed parameters, effect classification and dry-run support** are declared as metadata, because the verifier depends on them.
- JPMS gives encapsulation, not a sandbox. The working assumption is that **modules are trusted code** that the user installs deliberately. Rulesets are the untrusted part, and they can only reach modules through engine-checked capability calls. If untrusted third-party modules ever matter, process isolation can be added behind the same capability interface.

### Permission model
- **Default deny.** Grants live in a **local policy file outside the ruleset repos**, with **one grant set per layer**, so a private layer and its public upstream hold separate grants.
- **Scoped capabilities.** A grant names a capability plus constraints on its arguments (e.g. `mail.move` only on account "work" and only to folders under `Archive/`). Modules declare in their metadata which parameters can be scoped.
- **Credentials by local binding.** A rule uses a local name (e.g. `mail-account:work`). A local binding maps the name to the real account and secret and limits it to specific capabilities. Rulesets never contain or see secrets.
- **Effective permissions** are the intersection of what the rules declare and what the user granted. The engine enforces this on every capability call.
- **Destructive and external effects** require an explicit grant.
- **Only the user can apply grants.** The AI can propose grants but never apply them. A ruleset update that needs more access produces a **permission diff** and needs a new grant first.
- **Runtime prompting as a fallback.** When a rule needs something that is not granted, the engine does not block. It disables that rule, queues an approval request and notifies the user. The user answers in a frontend with allow once, allow always (which creates a scoped grant) or deny. The AI cannot answer prompts.
- **Audit log** in SQLite of every capability call and every grant change. Grants can be revoked.

### Frontend and views
- **The frontend is a generic renderer with no functionality of its own.** It displays what the daemon describes and sends user actions back as API calls (commands, approval answers). It holds no credentials and no rules.
- **FXML is not the source of UI descriptions.** FXML is JavaFX-specific and can reference controllers and scripts, which would bring code into the frontend and, for rulesets, execute untrusted code. The frontend may use bundled FXML only for its generic widget components, with no controllers beyond the generic ones.
- **The daemon describes the UI** through the local API. Sources:
  1. The engine's own screens: status, effective ruleset view, approval queue, grants, audit log.
  2. Commands: rules with a `command` trigger declare a title and typed parameters, and the frontend generates the form from them.
  3. Views declared by modules and rulesets.
- **Ownership split.** Modules provide data (read-only capability queries) and the default presentation of their data types as descriptions, not code. Rulesets decide what happens and which screens exist: a **view** composes data from queries into a screen with columns, buttons and commands. The daemon serves the description and runs the queries under the ruleset's grants.
- **View format.** A small vocabulary of our own in TOML, with a fixed catalog of components (table, list, detail, form, button, text). Values are literals or CEL expressions, the data source is a read-only capability call, and user actions are commands sent back to the daemon. These ideas are taken from A2UI, whose concepts match closely. A2UI (young, v0.8) and Adaptive Cards (SDKs for JavaScript, .NET, UWP, WinUI, Android and iOS, none for Java) were not adopted directly, because they are JSON-based and would not fit layering, CEL and the verifier without translation, and either way a JavaFX renderer would have to be written. The vocabulary stays simple enough to be translated to such formats later for other frontends.
- Views take part in layering and are checked by the verifier. The UI schema is versioned, so an older frontend can report that it does not understand a newer view.

Example view:
```toml
id = "view.newsletters"
title = "Newsletters this week"

[source]
capability = "mail.list"
args = { folder = { cel = "params.newsletter_folder" } }

[[component]]
type = "table"
rows = { cel = "source.items" }
columns = [
  { title = "From", value = "item.from" },
  { title = "Subject", value = "item.subject" },
  { title = "Date", value = "item.date", format = "datetime" },
]

[[component.row_action]]
label = "Open"
command = "mail.open"
args = { message = { cel = "item.id" } }
```

The daemon evaluates the source query and sends the frontend a resolved description. The frontend never runs CEL or queries anything itself.

### Build and runtime
- **Maven** with a multi-module build, on the latest LTS JDK.
- **Maven group ID `it.uhde`**, root package **`it.uhde.praksis`**. Artifact IDs are `praksis-<part>` (e.g. `praksis-capability-api`). JPMS module names equal the root package of the module (e.g. `it.uhde.praksis.capability.api`).
- The spike under `spikes/m0` still uses the placeholder `org.praksis.spike` and is not renamed.

### Repositories (decided 2026-10-29)
Praksis is split into repositories by what changes together, not all at once.
- **`Praksis` (core, one repository for now):** the capability API, the protocol, the expression layer, the ruleset model, the store, git access, the engine, the daemon and the CLI change together and are tested together. The modules stay here too until the capability API has settled; they already are separate Maven modules that depend only on the capability API, and the daemon already loads modules from a directory with a hash lock, so taking them out later is cheap.
- **The frontend is its own repository from the start (`Praksis-Desktop`):** a JavaFX application with its own jlink image, depending on the protocol module only. That keeps the frontend a generic renderer: it can do only what the daemon API allows. This needs the protocol published as a versioned artifact before M6 task 4.
- **Rulesets, views and their tests are separate repositories, as today** (`Praksis-Mail`, `myPraksis`). The views of a mail application belong in `Praksis-Mail`, as layers with their tests.
- **The mail modules move out later, together (`Praksis-Modules-Mail`: IMAP, Maildir, SMTP):** they share the mail contract (the event `mail.received` and the capabilities for moving, reading and sending mail), which is written down once in that repository (today it is only described in the README of `Praksis-Mail`). They move after the mail read and send capabilities exist and the API has settled, because the API changes most while those are added. Reasons for moving them: their own release cadence, a clear boundary for trusted code, and proof that the capability API is enough for someone who does not work on the core. Reasons for waiting: the API has had one author as its client, and publishing and versioning it early would freeze mistakes.
- **What the extraction needs first:** `capability-api` and `protocol` released as versioned artifacts with a stability promise (0.x is fine), a packaging format for a module (the jars and `module.toml` in one archive) and a command `praksis modules install` instead of copying a directory and running `praksis modules lock` by hand, a decision which modules the default image ships, and integration tests that can use modules built elsewhere.

### Approval policy for AI changes
Approval is tiered by what a change does:
- **Always needs the user's approval:** widening grants, new or changed rules with a destructive or external effect class, and edits to rules written by the user (the engine tracks the author of each rule).
- **Everything else** that passes the verifier can merge automatically, but it **runs in shadow mode first** and is promoted to live after a trial period if nothing unexpected shows up.
- The policy is a local setting. The strict version above is the default.

### AI scope
- Each layer has an **`ai_maintained` setting**, on by default for the user's private layers and off for upstream layers.
- For an upstream layer, the AI can prepare a change on a branch for the user to submit. It never pushes to a repo that is not the user's. Pushing to any remote always needs the user's action.

### Module trust and metadata
- Modules are **trusted code that the user installs deliberately**. There is no open third-party marketplace for now. A **local modules lockfile** records each module jar's hash, so a swapped jar is detected at startup.
- Capability metadata (name, typed parameters, effect class, scopable parameters, dry-run support, and the **JDK modules the module needs**, e.g. `java.sql`, which the runtime image must contain) is written as **annotations** in code. An **annotation processor in the Maven build generates a descriptor** (TOML or JSON) that ships inside the module. The verifier, the engine and the AI read the descriptor without running module code, and the build fails if annotations and descriptor disagree.

### Runtime prompting
- When a rule needs something that is not granted, **only that rule is disabled**. Other rules keep running, so nothing blocks and per-target ordering is preserved.
- Events the rule would have matched are kept in a **missed list**. When the user answers, they choose to **replay the missed events in order** or discard them. Retention is limited, by default 7 days or a count cap, and configurable.
- The approval request itself **never expires**.
- **Allow once** covers the single pending call. **Allow always** creates a grant scoped to exactly what was observed (the capability plus, for example, the specific account and folder). The user can narrow it. Widening beyond what was observed takes a deliberate edit, and there are no wildcard grants unless the user chooses one.

### Code structure (M1)
Maven modules, all under group `it.uhde`, in one repo (the spike under `spikes/` is not part of the build):

| Module | Purpose |
|---|---|
| `praksis-parent` | parent pom: versions, plugins, formatting, license headers |
| `praksis-capability-api` | the API modules implement; the only thing modules depend on |
| `praksis-expression` | our expression interface (compile, scope, bindings); knows no expression language |
| `praksis-expression-cel` | the CEL implementation, shaded into one jar; the only place that knows cel-java and protobuf |
| `praksis-ruleset` | rule model, TOML loader, static validation |
| `praksis-store` | SQLite persistence; the only place that knows the SQLite driver |
| `praksis-git` | fetches layers from git repositories by running the installed `git`; no dependencies |
| `praksis-engine` | module loader, event bus, dispatcher, capability invocation |
| `praksis-protocol` | request and response records shared by the daemon and the CLI |
| `praksis-daemon` | `main()`, lifecycle, local API server |
| `praksis-cli` | the `praksis` command |
| `modules/praksis-module-maildir` | first module: `mail.received` event, `mail.move` capability |
| `praksis-integration` | tests that run the real daemon and CLI as processes, including a SIGKILL restart check |
| `praksis-dist` | the `jlink` runtime image with the modules and the CEL layer next to it |

- Dependency rules: modules depend only on `praksis-capability-api`. Only `praksis-expression-cel` sees cel-java, and only modules see Camel. The engine finds the expression implementation through `ServiceLoader`. `praksis-ruleset` depends on `praksis-expression` and `praksis-capability-api`. `praksis-engine` depends on `praksis-ruleset`, `praksis-store`, `praksis-expression` and `praksis-capability-api`. The daemon and the CLI share only `praksis-protocol`.
- Hooks built into M1 so later milestones need no refactoring: every capability call goes through an `AccessPolicy` interface (allow-all until M3), the audit log is a hook with a no-op implementation, and the dry-run flag is part of the capability context.
- **Module descriptors** are written by hand as a `module.toml` inside each module in M1. The annotation processor that generates them is added before M4, and it targets the descriptor format defined in M1.
- **cel-java is shaded.** Its jars share packages, so they cannot be separate JPMS modules, and automatic modules cannot go into a `jlink` image. `praksis-expression-cel` therefore shades cel-java, protobuf and guava into one jar (an automatic module) that the daemon loads in its own layer, like a module. Expressions see an event as `event.data` (the typed core fields from the descriptor) and `event.extras` (the free-form rest). List and map fields are untyped (`list<dyn>`, `map<string, dyn>`) until field descriptors get element types.
- **Ruleset layout (M1, one layer):** a directory with `ruleset.toml` (`format_version`, `name`, optional `[param.<name>]` tables with `type` and `default`) and `rules/<id>.toml`. The rule ID must equal the file name. Rules fire in ID order, since a directory has no declaration order. A rule has `id`, `effect`, `needs`, optional `description` and `required`, one `[trigger]` and `[[action]]` tables. An action is either a capability call or `stop = true`. Unknown keys are errors, so typos in AI-written files are caught. Only `kind = "event"` triggers exist in M1.
- **Static validation** (`RulesetValidator`) checks against the module descriptors: event types and capabilities exist, argument names, required arguments and literal types match, expressions compile against the types they can see (filters must be boolean, arguments must match the parameter type, `results.<id>` only from earlier actions), `needs` lists every capability the rule uses, the declared `effect` is at least as strong as the strongest capability (order: read-only, local-write, destructive, external), and no action follows `stop`. The loader and the validator report all problems at once.
- **Store (M1):** one SQLite file in WAL mode with `synchronous = FULL`, schema version in `PRAGMA user_version`. Table `event` holds the event as JSON (timestamps and bytes are tagged so they keep their types), its state (`pending` or `done`) and a unique idempotency key. Table `run_log` holds what happened per event, rule and action. An event is stored before anything handles it and marked done afterwards, so handling is **at least once**: a crash in between repeats the event after the restart, and capabilities receive an idempotency key to make that harmless.
- **Dispatcher (M1):** `Engine` validates and compiles the ruleset once (the validator returns compiled rules), checks that every needed capability has an implementation and every parameter has a value, then handles events. Per event, matching rules fire in ID order. A failed filter evaluation or action is logged, the rest of that rule is skipped and the next rule continues. A failing `required` rule ends the event. `stop` ends the event without error. Events of one target run one at a time in arrival order, different targets in parallel (virtual threads). Every capability call passes the `AccessPolicy` and is reported to the `AuditLog`; both are hooks with allow-all and no-op defaults. The idempotency key of a call is `<event id>/<rule id>/<action id>`. `Engine.recover()` re-queues stored events that are not done. Not in M1: rules emitting events, conflicting-effect detection and retries.
- **Module loader (M1):** the modules directory has one subdirectory per module with `module.toml`, the module jar and the jars it needs. `module.toml` has `format_version = 1`, `name`, `version`, `module` (the JPMS module providing the services), `jdk_modules`, `sources`, `[[capability]]` tables (`name`, `effect`, `dry_run`, `params` and `results` as inline field tables) and `[[event]]` tables (`type`, `fields`). Unknown keys are errors. Each module is loaded in its own `ModuleLayer` below the boot layer, with the platform class loader as parent, and found through `ServiceLoader`. What `module.toml` declares must equal what the module provides, in both directions. `modules.lock` holds one SHA-256 per module over the names and contents of all files in its directory: a module that is not in the lockfile, or has changed since, is not loaded, and `ModuleLoader.lock` accepts the current state. A missing JDK module is reported by name. Local settings for a module (`[module.<name>]` in the daemon configuration) are passed once through `configure(settings)` on each capability and event source. The CEL implementation is loaded from its own directory with `ModuleLoader.loadExpressionCompiler`.
- **Maildir module (M1):** `modules/praksis-module-maildir`, JPMS module `it.uhde.praksis.module.maildir`, settings `root` (the Maildir directory) and optional `poll_interval_ms` (default 1000). The source `maildir.inbox` polls `new/` and emits `mail.received` (`message`, `folder`, `size`, and the headers `from`, `to`, `cc`, `subject`, `message_id`, `date`, `list_id`, `precedence` and `x_spam_flag`, empty if the mail has none; RFC 2047 words are decoded). The target is `mail:<unique name>` and the idempotency key is `maildir:<unique name>`, where the unique name is the file name before the first colon, so a mail that is still in `new/` after a restart is announced again and dropped by the store. The capability `mail.move` (`message`, `folder`; effect local-write, supports dry run) moves a mail into `cur/` of a Maildir++ folder (`INBOX` is the root, `Archive` is `.Archive`), keeps the flags, creates missing folders, refuses paths outside the Maildir and folder names that could escape it, and is idempotent: if the mail is gone from its old place but is in the target folder, it succeeds and reports where it is. Polling is used because a watch service is not reliable on network file systems. Thunderbird stores mbox by default, so this module is a test source and a source for `mbsync`, `getmail` and Dovecot users; IMAP follows after M1.
- **Layers (M2):** a layer is a directory (a git repo or a path) with `ruleset.toml` (`format_version`, `name`, optional `[param.*]`) and any of: `rules/<id>.toml` adds a rule whose id does not exist below; `replace/<id>.toml` is a complete rule plus `based_on`; `patch/<id>.toml` has `[[change]]` tables with `path`, `expect` and `value` (or `remove = true`) and an optional `based_on`; `disable/<id>.toml` has `based_on` and an optional `reason`. `based_on` is `sha256:` of the rule below as shown in the effective view, computed from the parsed rule, so formatting and key order do not matter. A patch checks field by field: `expect` is the value the field must have now, and without `expect` the field must be absent. So an upstream change to another field of a patched rule does not matter, and a change to the patched field is an error. Patchable paths are `description`, `effect`, `required`, `needs`, `trigger.type`, `trigger.filter`, `action.<id>.capability` and `action.<id>.args.<name>`. A patch is applied to the rule in its TOML shape and the result goes through the normal rule loader, so it is checked as strictly as a file. A layer sees the rules as they are below it and may do one thing to a rule. A disabled rule stays in the effective view as disabled and cannot be added or changed by a higher layer. Missing targets and changed targets are errors for the whole combination, with all problems listed. Rules still fire in id order (a directory has no declaration order, so layer position does not matter), parameters merge by name (a higher layer may change the default, not the type) and values in `praksis.toml` win. The ruleset name is the layer names' ruleset names joined by `+`.
- **Git access (M2):** `praksis-git` has the interface `GitSource` (`resolve(name, url, ref)` gives a commit id, `export(name, url, commit, target)` writes the files of a commit into a new directory) and the implementation `GitCli`. It keeps a bare repository per layer under a cache directory, fetches all branches and tags, and reads the files with `ls-tree` and `cat-file --batch`, so nothing is ever checked out and no hook, filter or attribute runs. The export is written to a temporary directory and renamed, so a snapshot is complete or absent. A commit with a symbolic link or a submodule is refused, as are file names with `..` or `.git`. Authentication is that of the user's git (SSH keys and agent, credential helpers); git never prompts, because the daemon has no terminal. Only the transports file, git, http, https and ssh are allowed, which excludes `ext::`, and addresses and refs that look like options are refused. A pinned commit that is not in the local copy is fetched on export; one that the server no longer has (rewritten history) is reported. Not covered: a machine without git, and signatures of commits or tags.
- **Layer configuration and pins (M2):** `praksis.toml` lists the layers bottom to top as `[[layer]]` with `name` and either `git` and `ref` (the branch or tag to follow) or `path` (a directory that is read as it is and never pinned). Without any layer, the directory `ruleset` is used as before; `ruleset` and `[[layer]]` cannot be mixed. `[param]` gives values for ruleset parameters. `rulesets.lock` holds one `[layer.<name>]` table per git layer with `git`, `ref` and `commit`; the files of a pinned commit live in `layers/<name>/<commit>`, the local git copies in `cache/git`. Starting the daemon uses only the pins: a git layer without a pin, or whose `git` or `ref` differs from its pin, stops the start with the command to run, and a missing snapshot is fetched. `praksis layers update [--dry-run] [layer...]` is the only thing that asks a server: it finds the latest commit of each ref, puts the layers together, checks the result against the loaded modules (the same checks as at start) and writes the pins only if all of that is fine. Otherwise it lists the problems and leaves the pins alone. Its report shows the commit moves and which rules were added, changed or removed. `praksis layers status` shows the pins offline, `praksis effective` shows the ruleset that would run: every rule in firing order with its `sha256` for `based_on`, what each layer did to it, disabled rules with their reasons, and the parameters. All three run through `java -m it.uhde.praksis.daemon --admin ...`, so they work without a running daemon. A new pin takes effect when the daemon restarts; there is no reload yet.
- **Writing rules (what the first real rulesets showed):** `mail.move` moves the file, so a rule that moves a mail must end with `stop`; a later rule would find the mail gone. Rules fire in id order, so ids carry the priority, in the style of `conf.d` files: `mail.10-spam`, `mail.20-lists`, and a personal rule that must come first is named `05.vip`. The standard CEL macros (`exists`, `all`, `filter`, `map`, `exists_one`, `has`) are available in expressions; string extensions such as `lowerAscii` are not, `matches('(?i)...')` does the job. The first public ruleset is drafted in `Praksis-Mail` (rules `mail.10-spam`, `mail.20-lists`, `mail.30-bulk` with the parameters `spam_folder`, `lists_folder` and `bulk_folder`), the personal layer in `myPraksis` (rule `05.vip`, a patch of the lists rule).
- **The mail contract (backend-neutral):** every mail backend provides the event `mail.received` and the capability `mail.move`, with the same fields, so one mail ruleset works with all of them. The event has `message` (an opaque id of the mail that only the backend understands: a path for Maildir, a UID with its validity for IMAP), `folder`, `size`, and the headers `from`, `to`, `cc`, `subject`, `message_id`, `date`, `list_id`, `precedence` and `x_spam_flag` (empty if absent). `mail.move(message, folder)` moves a mail to a folder by name and answers with the new `message` id; repeating a move whose mail already is in the target folder succeeds. Rules pass `event.data.message` to `mail.move` and never look inside the id. Two backends cannot be loaded together (they provide the same names), so `praksis.toml` has `enabled_modules = ["..."]`, which by default lists the modules that have a `[module.<name>]` section (or all modules if there is none); modules that are not enabled stay installed but are neither read nor checked against the lockfile.
- **IMAP module (M2.5):** `modules/praksis-module-imap`, JPMS module `it.uhde.praksis.module.imap`, built on **Angus Mail (Jakarta Mail) directly, not Camel**: the IMAP needs here (stable identity, a real MOVE, UIDs, later IDLE) are exact, and Camel would add its core jars for nothing; Camel stays an option for modules where it helps. It is loaded from disk with the four Angus/Jakarta jars in its own directory and needs the JDK modules `java.desktop`, `java.xml` and `java.logging` (Angus Mail requires them), which is why the image has them (+13 MB). Settings `[module.imap]`: `host`, `user`, `password_command` (a command whose output is the password, e.g. `["pass", "show", "mail/example"]`; nothing secret is stored, the command is run again on every new connection, its output never appears in a message), `security` (`ssl` default, `starttls`, or `none` for localhost only), `port`, `folder` (default `INBOX`), `initial` (`unseen` default, `all`, `none`: what is handled when the folder is first seen), `poll_interval_ms` (default 30000), `timeout_ms`, `ca_file` (an extra certificate authority). TLS verifies the certificate and the host name. The source `imap.inbox` polls the folder read-only with `peek` and announces every mail with a higher UID than the last one announced, whether read or not. The mail is named by an opaque `message` id `imap:<folder>:<uidvalidity>:<uid>:<Message-ID>` (the parts base64url); the idempotency key is `imap:<user>@<host>:<folder>:<uidvalidity>:<uid>`, so a restart announces what is still there and the store drops it, and a renumbered folder (new UIDVALIDITY) counts as new. `mail.move` uses MOVE if the server has it, else COPY + `UID EXPUNGE` (UIDPLUS), and refuses a server with neither, because a plain EXPUNGE would remove mails that the user marked as deleted. The new place of the mail comes from the server's `APPENDUID` answer, no search. A repeated move whose mail is gone from its folder looks for the Message-ID in the target folder and succeeds if it is there; a mail without a Message-ID cannot be found that way. Folder levels are written with `/` and translated to the server's separator. Missing target folders are created. One connection serves all moves, one at a time.
- **Local API** between the CLI and the daemon: a Unix domain socket with JSON messages, not HTTP on localhost, so access is controlled by file permissions (the daemon sets the socket to `rw-------`). The wire format is one JSON object per line (UTF-8, at most 1 MiB), requests carry `op` and responses carry `type`; unknown fields are errors. Requests in M1: `status`, `inject` (type, optional target and key, data), `log` (limit), `stop`. A connection may send any number of requests. The messages are records in `praksis-protocol`, which also holds a small `Client`; the daemon and the CLI share nothing else.
- **Permissions (M3):** `<home>/policy.toml` is the only place for grants; it is always in the home, cannot be moved by `praksis.toml` and is not part of any ruleset. It has `format_version = 1` and `[[grant]]` tables with `id`, `layer`, `capability`, optional `note` and `[grant.args]`, where an argument name maps to one matcher: `{ equals = ... }`, `{ one_of = [...] }` or `{ prefix = "..." }`. A matcher is allowed only on parameters that the module descriptor marks `scopable`, `prefix` only on strings; an argument without a matcher is not restricted. Without a file nothing is allowed. At start the daemon checks the grants against the modules and the configured layers and refuses to start if a grant names a layer or capability that does not exist. `GrantPolicy` answers each capability call from the grants of the layer that owns the rule; the owner is the layer that last added, replaced or patched it (`LayerStack.Origin.owner`, while `layer` stays the layer that added it), so a private patch on a public rule needs a grant of the private layer. A denied call is logged with the outcome `DENIED` and a reason such as `layer 'mail' has no grant for mail.move (folder=Trash)` (only scopable arguments are shown), recorded in the audit hook, and disables that rule only: later events that match its filter are logged as `SKIPPED` ("rule is disabled"), a disabled `required` rule ends the event like a failure. Rules whose events are in flight at the same time may each be denied once before the first denial is noticed. A rule that made earlier calls before the denied one keeps their effects. The disabled state is in memory: a restart evaluates it again and disables the rule on the first denied call. The audit log and the missed list are in the database (schema version 2, old databases get the tables when they are opened). `audit` has one line per capability call, allowed or denied, with the rule, the capability, the arguments as evaluated (as JSON, so they can contain whatever the rule passed; the run log does not) and the error; it is written after the call was decided and carried out, so a crash in between leaves no line and the repeat after the restart is recorded. A failing audit write is reported on stderr and does not stop the work. At every start the daemon also writes a `POLICY` line with the SHA-256 of `policy.toml` and the grant ids if they differ from the last such line, so a change made outside the daemon shows up. `GRANT` lines are for grant changes made through the daemon (task 4). `praksis audit [-n N]` shows the newest lines first. `missed` holds one row per rule and event, written when a rule's call is denied (for that event) and whenever a disabled rule's filter matches; it keeps 7 days and 1000 events per rule (constants for now), and the event itself stays in the event table, so a replay can read it. Approvals follow below.
- **Approvals (M3):** when a denied call disables a rule, the daemon opens a request (table `approval`, schema version 3) with the rule, its owner layer, the capability, the arguments of the refused call that a grant may restrict, and the event; a rule that already has an open request gets no second one. The state is `PENDING`, `DENIED`, `ALLOWED_ONCE`, `ALLOWED_ALWAYS`, `COVERED` (a grant added by hand now covers it) or `STALE` (the rule is gone). At start and after `grants reload` the daemon brings the disabled rules in line with the open requests, so a pending or refused rule stays disabled across a restart. `praksis approvals` shows the requests, the disabled rules with the reason and how many events each rule missed. `approvals allow <n> --once` lets the one denied event through without any grant (the rule is enabled again, and its next call without a grant opens a new request). `allow <n> --always (--replay|--discard)` appends a grant to `policy.toml` for exactly the observed scopable arguments (`equals`), id `approval-<n>`, with a note; it has to say what to do with the missed events, which are replayed in order in the background (the replay stops, keeping the rest, if the rule is denied again) or dropped. `deny <n> [--discard]` keeps the rule disabled. A rule that a hand-edited grant freed (`COVERED`) keeps its missed events until `approvals replay <rule>` or `approvals discard <rule>`. `praksis grants` lists the grants in effect, `grants revoke <id>` removes one from the file (the text of the rest of the file is kept; the new file is loaded and checked before it replaces the old one), `grants reload` reads a hand-edited file again and refuses it, keeping the old grants, if it is invalid. Every answer and every grant change is an audit line (`APPROVAL`, `GRANT`). Only the CLI on the local socket answers; the AI maintains rulesets, which cannot reach `policy.toml` or the socket. Not done: notifying the user (the daemon logs a warning), time limits on grants, and a replay that keeps pace with live events of the same target.
- **Credentials (M3):** `policy.toml` can hold `[credential.<name>]` tables (the name is lower case letters, digits, `.`, `_`, `:` or `-`, so `imap:work` is written `[credential."imap:work"]`) with `command` (the program and its arguments; what it prints, without the final line break, is the secret), `capabilities` (the capabilities and event sources that may ask for it) and an optional `note`. Praksis stores no secret. A module gets a `Credentials` object through `useCredentials` (a default method of `Capability` and `EventSource`, called after `configure` and before any other method) and calls `secret(name)`. `CredentialResolver` answers from the policy in use at that moment, so an edited policy applies to the next request. It refuses a name that has no binding and a part that the binding does not name, runs the command (30 seconds, error output discarded, 64 KiB at most) every time, and writes a `CREDENTIAL` audit line for each request, allowed or refused, with the name and the asking part. The secret is never stored, logged or put into an error message, and a failing command's output is dropped. The names in `capabilities` are checked at start against the modules (`policy.toml: credential 'x': no capability or event source named 'y'`). The IMAP module takes `credential = "<name>"` as an alternative to `password_command` (exactly one of them); both the source (`imap.inbox`) and the move (`mail.move`) have to be named in the binding. `password_command` keeps working but is neither audited nor limited. `praksis grants` also lists the bindings with the program (not its arguments) and who may ask. Not done: rules that name a credential themselves (there is one account per module for now, chosen in the module settings), a CLI to add bindings (edit `policy.toml`, then `praksis grants reload`), and secret stores that need Praksis to talk to them directly.
- **Verifier (M4):** `Verifier` (in `praksis-ruleset`) is deterministic and read-only. It returns a `Report` of `Finding`s (severity `ERROR` or `WARNING`, the check, where, what; errors first). Checks so far: `validate` (everything `RulesetValidator` finds), `unused-need` (error: a rule lists a capability in `needs` that none of its actions calls, because a rule may only ask for what it uses), `effect-overstated` (warning: a stronger effect class than its capabilities have), `shadowed` (warning: a rule with no filter that stops handles every event of its type, so later rules of that type can only fire if it fails before the stop), and `empty` (warning). `praksis verify` (admin command, no daemon needed) runs these on the ruleset that would run and adds the `policy` check: `policy.toml` must be valid and its grants and credential bindings must name layers, capabilities and event sources that exist. It prints one line per finding and exits 1 if there are errors.
- **Permission requirements (M4):** `Permissions` works out from the rules alone what a ruleset needs: one `Requirement` per kind of call, made of the owner layer (whose grants decide), the capability, and the arguments a grant may restrict (`scopable` parameters). An argument is *known* if it is a literal, `params.<name>` (folded to the parameter's value) or a quoted string in an expression; every other argument, and a missing one, is *unbounded* and only a grant that does not restrict it covers it. `Permissions.diff` gives the requirements that are new or gone between two rulesets; `uncovered` asks the policy the same question as the engine. `praksis verify` reports each uncovered requirement as an `access` warning. `praksis layers update` prints the diff, and refuses (exit 1, pins unchanged) if a requirement is new and not covered; `--accept-new-access` moves the pins anyway (the calls are then denied at run time until granted). There is no gate for the first pin, as there is nothing to compare with.
- **Ruleset tests (M4):** `tests/<rule id>.toml` in a layer holds `[[test]]`s of that rule: a name, an `[test.event]` (`type`, `data`), optional `[test.params]` (parameter values for this test; otherwise every test runs with the defaults of the layers, not with the values in `praksis.toml`, so tests shipped in a public layer do not depend on the local configuration), optional `[test.mock."capability"]` results, and the calls the rule must make, in order, as `[[test.call]]` (`capability`, `args`; only the listed arguments are compared; no `call` means the rule makes none). `RuleTestRunner` (in `praksis-engine`) runs each test on the real `Engine` with a temporary store and a recorder in place of every capability, so nothing outside the process is touched, and checks the calls of the rule under test (other rules that fire for the event are ignored). A rule that fails in the test fails the test. The tests of layer k run against the stack up to and including k, so a layer is tested against what it sees. A rule counts as *fired* by a test if it matched and ran; task 4 uses this for coverage. `praksis test` runs all layers, prints one line per test and exits 1 on any failure or unreadable test file.
- **Coverage (M4):** `praksis verify` also runs the tests and adds two kinds of ERROR: `test` (a test fails or its file cannot be read) and `coverage` (no test in the rule's owner layer, in a file named after the rule, makes it fire). The owner is the layer that last defined the rule, so a private patch needs a test in the private layer, and a rule that an upstream update changes in a way that stops its tests from firing is reported at the next `praksis verify`. The check is not part of `layers update` yet.
- **Candidates and replay (M4):** `praksis verify` can check a ruleset other than the one in use: `--update` (the pins moved to the latest commits, as `layers update` would), `--layer name=<directory>` or `--layer name=@<ref>` (a layer replaced by a directory, or by a branch or tag of its own repository, so the AI's branch of the private layer can be checked before it is merged; repeatable). All checks (validation, tests, coverage, policy) then run on the candidate, and access that is new compared with the ruleset in use and that no grant covers is an ERROR instead of a warning. `--replay [-n N]` takes the newest N (default 200) stored events, whatever their state, runs each through the ruleset in use and through the candidate (the real engine, a temporary store, recorders instead of capabilities that return the declared results as default values) and lists the events whose calls or failures differ, up to 20, as `now:` and `candidate:` lines. Differences are information, not errors, since a change is meant to change something. Without a candidate the replay compares the ruleset with itself. The database is opened as the daemon does (WAL), so it works while the daemon runs. Events whose rules read results of earlier calls see defaults (empty string, 0, false), not what the real call returned.
- **Shadow mode (M5):** off unless `[shadow] enabled = true` in `praksis.toml` (also `trial_days`, default 7, and `min_events`, default 20); it is off by default until the approval tiers (task 3) decide which changes need it, because turning it on changes what a new or changed rule does. The first start with it on takes the rules in use as promoted (table `promoted`, with the rule as JSON, schema version 4). From then on a rule whose `(id, hash)` is not promoted is on trial (`shadow_rule`): if an older promoted version of the id exists it keeps running live, otherwise the rule does not run at all, and the new version is placed before it in the firing order and only observed. The engine takes the live ruleset and the rules on trial separately (`Engine(live, shadow, ...)`). An observed rule is evaluated like a live one (filter, arguments, results as default values) for the events that reach its place in the order; the calls it would make are recorded with the arguments as evaluated and whether the grants would allow them (`shadow_run`, 1000 per version), a failure is recorded as "would fail", nothing is called, nothing is audited, a denial disables nothing, and its `stop` does not end the event for the rules after it. `praksis shadow` shows per rule the start of the trial, whether it replaces a running version, how many events it was seen with, for how many it would call, would be refused and would fail, whether the trial period and the number of events are met, the hash, and the last five events with what it would call and which rules really handled the same event. `praksis shadow promote <rule>` records the version as promoted, ends the trial and swaps it in at once (the older version is gone); `praksis shadow reset <rule>` forgets the observations and restarts the trial. The daemon never promotes by itself. There is no `discard`: throwing away a change is done in the layer (git), and a version that is changed again or removed ends its trial at the next start. Not done: a notification when a trial is over, and shadow mode for rules that the engine runs because of a replay.
- **Provenance (M5):** `GitSource.lastChange(name, commit, file)` gives the last commit that changed a file (author, email, time, subject, body), from the local copy only (`git log -1` on the bare repository; a commit that is not at hand gives nothing, and the file name must be `rules|replace|patch|disable/<id>.toml`). For a rule, the file is the one with which its owner layer (the layer that last added, replaced or patched it) defined it, looked up at the commit the layer is pinned to; a directory layer has no history. The commit counts as **AI** if its message has the trailer `Praksis-Author: ai` or a `Co-Authored-By` line that names Claude or anthropic.com, otherwise as **human**, and a rule without history is **unknown**. This is the commit author's claim, not proof, so the approval tiers (task 3) must not treat "human" as trusted on its own; the reasoning is the message without the `Praksis-`, `Co-Authored-By` and `Signed-off-by` lines (at most 1000 characters). `praksis effective` shows under each rule who changed it last, in which commit, the subject and the first lines of the reasoning. At every start the daemon writes an audit line of the new kind `RULE` for each rule whose hash differs from the last `RULE` line about it (subject = the hash, detail = layer, file, history, author kind, name, email, commit, subject, reasoning, and the result of the static checks on the whole ruleset at that moment, "static checks: N error(s), M warning(s)"); a change made in a layer shows up at the next start, whoever made it, and a start without a change adds nothing. The result of the tests and the replay is not part of it yet; the proposal workflow (task 5) records the full report.
- **Approval tiers (M5):** `policy.toml` gets two sections. `[trust] human_keys = [...]` lists the user\'s signing keys (gpg fingerprints or key ids, matched against the end of the fingerprint with 8 characters at least, or SSH fingerprints such as `SHA256:...`). A commit is **human** only if git finds its signature good (`%G?` is `G` or `U`, so git\'s own keyring or `gpg.ssh.allowedSignersFile` decides what a good signature is) and the signer is one of these keys; it is **ai** if it is not and the message says so; otherwise **unverified**; the author name and the message prove nothing. `GitCli` takes extra `-c key=value` settings, and the user\'s own git configuration applies. `[approval]` switches the strict rules off one by one (`widening_access`, `destructive_or_external`, `user_rules`, `shadow_first`, all true by default). `Tiers.decide` looks at every rule that is new, changed or removed between the ruleset in use and a candidate: **APPROVAL** if the rule needs access that no grant covers (new compared with the ruleset in use), if its effect class is destructive or external, if the version in use was human and the new one is not (or if a human rule is removed); else **SHADOW** (the rule is new or changed and runs in shadow mode first); **AUTOMATIC** only if `shadow_first` is off, and for the removal of a rule that was not human. The verdict is the strongest tier. `praksis verify` with a candidate (`--layer`, `--update`) prints the verdict and one line per rule with the reasons; it does not change the exit code. The daemon does not enforce it yet: applying a candidate and putting its rules into shadow mode is the proposal workflow (task 5), which will refuse to apply an APPROVAL change without the user\'s answer and will require `[shadow] enabled` for SHADOW. `ApprovalTiersIT` uses real repositories signed with an SSH key: the user\'s rule is human, a public rule is unverified, an AI edit that claims in its message to be a person\'s needs approval, the same edit signed with the user\'s key only goes to shadow mode, a new rule within the grants goes to shadow mode, one needing an ungranted folder needs approval, and switching the rules off in `[approval]` changes the verdict.
- **AI-maintained layers (M5):** `ai_maintained = true|false` in a `[[layer]]` says whether an AI may propose changes to it. The default is true for a directory layer (`path`) and false for a git layer, because Praksis cannot tell whether a repository is the user\'s own; the user sets `ai_maintained = true` on their private git layer. It is shown by `praksis layers status` (`[AI-maintained]`) and read by `DaemonConfig.aiMaintainedLayers()`; the proposal workflow (task 5) takes proposals for these layers only. For any other layer a change can still be checked with `praksis verify --layer`, and the AI may prepare a branch for the user to submit upstream, but Praksis never applies it, and never pushes to a repository: pushing always needs the user\'s own action.
- **Proposals (M5):** a proposal is a branch (other than the layer\'s `ref`) of an AI-maintained git layer that is not part of what the layer is pinned to (its tip is not the pin nor an ancestor of it) and has not been decided. The commands run as admin commands without a daemon and use the local copy of the repository after fetching it. `praksis proposals` lists them (`layer@branch`, tip, number of commits, the last three with author, how the commit counts and subject). `proposals show <layer>@<branch>` prints every commit with its signature status and its reasoning, then runs everything that `praksis verify --layer <layer>=@<tip> --replay` runs (validation, tests, coverage, access, the tier of the change, the replay) and ends with the command to approve exactly this commit, or says that it cannot be approved while there are errors. `proposals approve <layer>@<branch> <commit>` needs the commit that was looked at (7 characters at least) and refuses if the branch has moved, if the checks find errors, or if the tier is SHADOW while `[shadow]` is off (unless `--without-shadow`); otherwise it pins the layer to that commit (keeping the configured address and ref) and writes an audit line of the kind `PROPOSAL` with the decision, commit, tier, result of the checks, the rules with their tier and the commits with their authors. The approval itself is the user\'s answer for the APPROVAL tier. The daemon uses the new pin after a restart, and with shadow mode on the new and changed rules are on trial. Praksis does not merge or push: the user merges the branch into the ref, and until then the next `praksis layers update` moves the pin back to the ref (the message says so). `proposals reject <layer>@<branch> [reason]` records the reason (`PROPOSAL`, rejected); decided commits are not listed again, a branch that moves is a new proposal. Only git layers with `ai_maintained = true` take proposals; directory layers have no branches. `GitSource` gained `branches`, `commits(base, tip)` and `isAncestor`. The checks of `praksis verify` moved into `Admin.check` and `Admin.print`, which the proposals reuse.
- **Screens API (M6):** the requests and responses of the protocol (`Request`, `Response`, JSON lines on the socket, one connection may send any number) for the engine screens, all worked out by the same code as the command line and with the modules the daemon has loaded (`Screens` in the daemon; `Admin.check` and `Proposals` take the modules of the caller). `Changes(since, waitMillis)` answers with a counter and the topics that changed after it (`events`, `log`, `approvals`, `shadow`, `audit`); with 0 it returns every topic at once, otherwise it waits up to 30 seconds for the next change (a virtual thread per connection, so waiting is cheap), and a client keeps its screens current by sending the counter of the last answer in a loop. The store reports every write through `Store.onChange(topic)`, called while it is locked, so the topics cannot be forgotten by a new writer; a change in the files of a layer is not a topic (use `Layers` and `Effective`, whose `pinsChanged` says that a restart would use other rules). A client may be answered at the first change (for example `events`) before the related write (`log`), and asks again. `Effective` gives the rules in use with layer, owner, hash, history, who wrote the current version (human, ai, unverified, unknown), the reasoning and whether a version is on trial, the parameters and the disabled rules. `Layers` gives each layer with its source, pin, whether the configuration differs, whether the files are on disk and whether an AI may propose changes. `LayersUpdate(dryRun, acceptNewAccess, names)` answers with the report as lines, `Verify(replay, count, update, replacements)` with the findings, the tier and the reasons per rule, and the replay (at most 20 differences), `Proposals`, `ProposalShow`, `ProposalApprove(name, commit, withoutShadow)` and `ProposalReject(name, reason)` mirror `praksis proposals`; approving and rejecting answer with the same lines as the command line. `Stop`, the approval and shadow requests of M3 and M5 stay as they are. Not done: pushing a message from the daemon to a client without a request (the long poll replaces it), and a version number of the protocol (the frontend repository will need one before it is released).
- **Commands (M6):** a rule with `[trigger] kind = "command"`, a `title`, an optional `description` and `[[trigger.param]]` tables (`name` lower case with digits and `_`, `type` as for parameters, `required`, `default`, `label`; a parameter with a default is not required, and cannot be said to be) is a command: something that only a person starts. It is an ordinary rule in every other way (`effect`, `needs`, actions, layering with replace and patch, tests, provenance, the hash), so its calls need grants of its owner layer like any rule\'s, a denied call disables it and opens a request, and a command that is destructive or external needs the user\'s approval as a change. The arguments a person gives are the data of an event of the type `command.<rule id>` (`Rule.eventType()`), checked against the declared parameters with the same coercion as an injected event (defaults fill what is missing, unknown or missing required fields are errors that say so before anything runs), and the actions read them as `event.data.<name>`, type-checked by the validator from the declared types. A command is tested like a rule with a test event of that type (`[test.event] type = "command.<id>"`). Commands are never on trial in shadow mode, since nothing would happen when a person starts an observed command, and the tier of a command that needs no approval is AUTOMATIC. API: `Commands` lists them (id, title, description, owner layer, effect, why it is disabled, parameters) and `RunCommand(command, args, client)` starts one, answered with the event id; `Outcome(event)` gives whether it was handled and its run log lines. Every start is an audit line of the kind `COMMAND` (command, event, client name, arguments). CLI: `praksis commands` and `praksis run <command> name=value ... [--no-wait]`, which waits for the result and exits 1 if a step did not succeed; list, map and bytes arguments are given through the API. Not done: a way to cancel a running command, results beyond the run log (a command that returns data to show), and confirmation prompts for commands with an external effect (the frontend decides how to ask).
- **Views (M6):** a view is a file `views/<id>.toml` of a layer: `schema_version` (default 1), `title`, optional `description`, state as `[param.<name>]` with a type and a default, read-only data as `[source.<name>]` (a `capability` and `args`), and `[[component]]`s. Values are literals or `{ cel = "..." }` expressions over `view` (the state), `source` (the results of the sources by name), `params` (the ruleset parameters) and, in the rows of a table or list, `item`; the expression layer gained dynamic variables for this (`Scope.dynamic`, `Bindings.dynamic`), which the verifier can only check for existence. Components: `text` (`value`, `style` normal, title, muted or code), `table` (`rows`, `columns` with a literal `title`, a `value` and a `format` of text, datetime, date, number or bytes, `empty`, `select`, `[[row_action]]`), `list` (`items`, `title`, `subtitle`), `detail` (`data`, `fields`), `button` (`label`, `command`, `args`, `confirm`, `enabled`), `form` (`command`, `defaults`, `submit_label`; the fields come from the typed parameters of the command) and the containers `row` and `column` (`[[component.children]]`, nested at most 4 deep, 60 components in a view). Clicking a row sets a view parameter (`select = { param, value }`) and the client asks for the view again: **the state is the client\'s and the daemon is stateless**, which is how a three-pane layout works without a stored selection. Layering: a higher layer adds views; to replace one of a lower layer it names the hash of the view it replaces in `based_on` (as `replace/` does for rules), a changed lower view is refused until looked at, and there is no patch or disable of views yet. The owner is the layer that last defined the view. The validator (`ViewValidator`, run by `RulesetValidator`) checks that the schema is not newer than `View.SUPPORTED_SCHEMA`, that sources call existing **read-only** capabilities with typed arguments, that commands named by buttons, row actions and forms exist and get the arguments they need, that `select` sets a declared parameter, and that every expression compiles with the variables it may use. Reading is checked like calling: the sources of a view need grants of the owner layer, `Permissions` counts them as requirements of `view:<id>` (so the verifier and the permission diff see them), and a changed view is a decision of the tier (AUTOMATIC, or APPROVAL if it reads what no grant covers). `ViewResolver` (daemon) turns a view into a description with values only (`ResolvedView`: parameters as used, components with rows, cells, selections, actions, forms), runs the sources under the owner\'s grants (`view:<id>` is the name the grants see; a denied call is an audit line), reports a source that is refused or fails as a warning, lets the components that depend on it say so (`error`) while the others still work, and never lets the frontend run an expression. Timestamps are ISO-8601 text and bytes Base64. API: `Views` and `ViewResolve(view, params, maxSchema)`; a client that sends the newest schema it knows gets an error for a newer view, which is how an older frontend reports one. CLI: `praksis views` and `praksis view <id> [name=value ...]` (a text rendering, for testing). The first read-only capability is `mail.list` of the Maildir module (folder, limit; id, from, subject, date, size and new, newest first), which is also the start of M6b task 1. **Decided against for now:** the default presentation of the data types of a module in its descriptor: results of the type list have no element types yet, so there is nothing to describe; it comes with the M6b spike, which will show what mail needs. Not done: charts and images, editing of data in a view (a form starts a command, nothing else writes), paging of long lists in the description (a source takes a limit), and views for the engine screens (they are the frontend\'s own).
- **Home directory (M1):** everything lives in one directory, `--home`, else `$PRAKSIS_HOME`, else `~/.praksis`: `praksis.toml` (optional), `policy.toml` (the grants), `ruleset/`, `modules/`, `modules.lock`, `praksis.db`, `praksis.sock`, `praksis.log`. `praksis.toml` has `format_version = 1`, optional `ruleset`, `modules`, `lockfile`, `database`, `expression` (the directory with the CEL jar; without it the class path is used), `dry_run`, and `[module.<name>]` tables that are handed to the modules. Relative paths are relative to the home. The socket path is limited to about 100 bytes, so the home must be short, and the daemon says so.
- **Daemon (M1):** `Daemon.start` loads the modules, finds the expression layer, loads and validates the ruleset, opens the store, queues unfinished events (`recover`), opens the API and only then starts the event sources; `close` goes the other way and lets queued events finish. It refuses to start if another daemon answers on the socket and replaces the socket of a dead one. An invalid ruleset, a changed module or a missing capability stops the start with all problems listed. `inject` checks the payload against the event type of the module descriptor (unknown or missing fields, types; timestamps as ISO-8601 strings, bytes as Base64) and answers with every problem at once.
- **CLI (M1):** `praksis [--home DIR] start | stop | status | inject <type> [--target T] [--key K] [--data JSON] | log [-n N] | audit [-n N] | verify`. Exit codes: 0 done, 1 failed, 2 wrong usage, 3 daemon not running. `start` runs the daemon as a separate background process with the same Java runtime and module path (`java -m it.uhde.praksis.daemon/...`), appends its output to `praksis.log`, waits until it answers and shows the end of the log if it does not.
- **Integration tests (M1):** `praksis-integration` runs at `verify` through failsafe. It copies the built jars into a module path (`target/mp`) and the CEL and Maildir jars into a home directory the way the daemon expects them (`lib/expression`, `modules/maildir`), then starts the daemon and the CLI as separate Java processes. The cases are: a mail is moved once and a restart after `kill -9` does not move it again, mails that arrive while the daemon is down are handled after the restart; 300 mails delivered in a burst while the daemon is killed twice with work left, afterwards every mail is in `Archive` exactly once and no action failed (a repeated event finds its mail already moved, which `mail.move` accepts); a stored but unfinished event whose mail is already in `Archive` is repeated harmlessly; the CLI commands against a daemon the CLI started itself. The module path must not contain any of the CEL jars: that jar is shaded and loaded from the home. `LayersIT` (M2) uses real git repositories made in the test: a public mail ruleset and a private layer with an added rule and a patch are pinned with `layers update` and sort five test mails as written; a compatible upstream update (a new rule, another field of a patched rule) is shown by `--dry-run` without changing the pins, then applied, and the daemon starts from the new pins although the upstream repository is gone; an upstream change to the very field a patch relies on is refused with the pins unchanged, and the daemon, killed and restarted, keeps working with the old pins. A mail that was handled before an update keeps its outcome: its event is stored as done, so a rule that is new does not reach back (replay of handled events is a later feature).
- **Runtime image (M1):** `praksis-dist` builds a `jlink` image (`target/praksis`, about 96 MB with a CDS archive) from the daemon and the CLI plus `java.logging` and `jdk.unsupported`, which the shaded CEL layer needs but the module graph cannot show. Every jar on the module path is a real module; sqlite-jdbc, Jackson and picocli all link. `bin/praksis` is the CLI. The Maildir module and the CEL jar are not in the image's module graph: they are copied to `lib/praksis/modules/maildir` and `lib/praksis/expression`. The daemon uses them when the home does not set `modules` or `expression` and has no `modules` directory of its own, so a fresh home needs only a ruleset and the module settings. `praksis modules lock` writes `<home>/modules.lock` for the modules that are in use (it runs the daemon's `--lock-modules`). The `--enable-native-access=org.xerial.sqlitejdbc` flag is passed when the CLI starts the daemon, not baked into the image, because the CLI would then print a warning for a module it does not load. All integration tests run against this image.
- **Footprint, measured at M1 (Linux, image, default JVM options):** the daemon answers about 0.7 to 1.0 s after start and has 150 MB resident when idle. After 300 to 500 mails it has 180 to 200 MB, and over 3 minutes of idling afterwards that stayed at 182 MB (threads fell from 50 to 33), so there is no growth. Other JVM options, 500 mails: SerialGC 208 MB, SerialGC with `-Xmx128m` 158 MB, SerialGC with C1 only 168 MB. No tuning is applied yet. `FootprintIT` fails above 400 MB peak or 10 s to start. Not yet measured: IMAP, real mailbox sizes, other operating systems.
- **Libraries:** Jackson (TOML and JSON), picocli (CLI), JUnit 5 with AssertJ (tests), the Xerial SQLite driver. Each is checked inside module layers when it is first introduced.
- **Build conventions:** Java 25, the Maven wrapper (Maven 3.9.9), `-Xlint:all` with warnings as errors, Spotless with google-java-format for formatting and SPDX headers (`./mvnw spotless:apply` fixes violations, and the check runs at `verify`), and an enforcer rule for the Maven and Java versions. google-java-format is pinned to 1.36.0 because 1.37.0 fails under the current Spotless Maven plugin. Modules are added to the parent pom with the milestone that introduces them.

### Verification (rulesets are maintained by an AI)
The verifier is deterministic code in the core. It is not an AI, and the AI maintaining rulesets cannot change it.
1. **Static checks**: schema validity, unique rule IDs, resolvable patch targets, existing capabilities, credentials referenced by declared name only, no loops between rules that trigger each other.
2. **Permission diff**: effective permissions before and after a change. A change that adds access cannot pass automatically.
3. **Tests that live with the ruleset**: example cases (given this event, expect these actions) with mocked modules. Rule changes must come with test changes.
4. **Replay**: past events from the engine history are run through the proposed ruleset with modules in dry-run mode, producing a behavioral diff.
5. **Shadow mode**: a new or changed rule can first run observe-only and be promoted after a trial period.

Workflow: the AI works on a git branch, never directly on the active ruleset. The verifier produces a report (checks, permission diff, behavioral diff). Every change records its author (AI or human), the reasoning and the verification result. Rollback is a git revert.

Consequences for the design:
- Rules declare an **effect classification**: read-only, local write, destructive, or external side effect.
- Modules must provide a **dry-run mode**.

## Roadmap

The first version is **M0 to M4**: headless (CLI only), mail processing as the only use case. The aim is to prove the new ideas (layered rulesets, permissions, verification) first. The GUI is a later client of the daemon.

- **M0, spike (go/no-go): done, verdict go.** cel-java type-checking of runtime-built event types, a dummy JPMS module in its own `ModuleLayer`, a Camel file component and IMAP endpoint inside a layer, and memory and startup with `jlink`. See `spikes/m0/FINDINGS.md`. Not covered yet: a real IMAP connection, layer unloading and Windows/macOS.
- **M1, walking skeleton:** `capability-api`, the daemon, the event bus with a SQLite queue, a loader for TOML rules, CEL evaluation, and one module with a `mail.received` event and a `mail.move` action (a local **Maildir** source first). The CLI starts the daemon, injects events and shows the log. Done when a mail dropped into the source is moved by a rule and a daemon restart does not process it twice. Real **IMAP via Camel** follows right after M1, unless the spike shows trouble.
- **M2, layers:** load rulesets from git with JGit, pin upstreams in a lockfile, apply `add`, `replace`, `disable` and `patch` from a private layer, support ruleset parameters, and add an effective-view command. Done when a public mail ruleset plus one private rule behaves as expected and survives an upstream update.
  - **Decided for M2 (2026-10-28):** layers are fetched with the **`git` command line** behind a small interface (so SSH keys and credential helpers of the user work for private repos, nothing is added to the image; JGit can be added behind the same interface later). A layer expresses changes with **one file per operation** (see "Layers (M2)"). Repos: `tuhde/Praksis-Mail` (public, the general mail ruleset) and `tuhde/myPraksis` (private, personal layer on top). Nothing is pushed to them without asking.
  - **M2 tasks:** (1) layer model and merge, no git: `Layer`, `LayerStack`, `RuleView` hash; (2) git source: fetch, resolve a ref, export a commit as a snapshot directory; (3) layer configuration and lockfile in the daemon, `praksis layers status|update`, `praksis effective`; (4) daemon builds the effective ruleset from the pinned snapshots, API operation for the effective view, parameter values from `praksis.toml`; (5) content: more mail fields from the Maildir module, draft `Praksis-Mail` and `myPraksis` locally and show them before anything is pushed; (6) integration test with local git repos: public ruleset plus one private rule, an upstream update that is applied, an upstream change that a layer was not written for and is refused.
- **M3, permissions: done.** The local policy file, grants per layer, scoped capabilities, credential bindings, enforcement at the capability call, the audit log, and the disable-and-queue behavior with a CLI to answer requests. Done when an ungranted rule is disabled, reported and can be approved.
  - **Decided for M3 (2026-10-28):** a grant restricts arguments with **declarative matchers** (`equals`, `one_of`, `prefix`), not CEL, so the M4 verifier can compare grants in a permission diff. Credentials are **named bindings**: `policy.toml` maps a name to the command that yields the secret and the capabilities allowed to use it; modules ask a resolver by name, and rules only ever see the name. A rule belongs to the layer that last defined it (the `layer` of its origin in the effective view), and that layer's grants decide.
  - **M3 tasks:** (1) policy model: `Policy`, `Grant`, `ArgMatcher`, strict `policy.toml` parser, check against modules and layers (done); (2) enforcement: the daemon builds a `GrantPolicy` from `policy.toml` and the effective view, a denied call disables that rule (done); (3) audit log in SQLite for calls and grant changes, and the missed list of events a disabled rule did not handle (done); (4) approval requests in the store and the CLI (`praksis approvals [allow|deny|replay|discard]`, `praksis grants [revoke|reload]`), allow once, allow always with a grant scoped to what was seen, replay or discard missed events (done); (5) credential bindings and a resolver for modules, IMAP can take its password from a binding instead of `password_command` (done); (6) integration tests (done): `PermissionsIT` runs the whole cycle through the CLI against the image with Maildir: an ungranted rule is disabled and reported, the missed mail waits, an answer with `--always --replay` adds the grant and moves the mail, new mail needs no question, a revoked grant makes the rule ask again, a refusal survives a restart, and the audit log shows every step. `LayersIT` shows that a private patch on a public rule is governed by the private layer's grants (the request names layer `mine`, the answer grants `mine`, the upstream layer's own rules keep working). `ImapIT` logs in through a credential binding (asked for by name, audited, the secret nowhere), shows that a binding that does not name `mail.move` stops moves, and kills the daemon with SIGKILL in the middle of a replay of 60 missed mails: after the restart `praksis approvals replay` finishes the job, every mail is in `Archive` once and no action failed.

- **M4, verifier: done.** Static checks, permission diff, ruleset tests with mocked modules, dry-run, and replay with a behavioral diff. Shadow mode comes last. Done when the verifier rejects a deliberately broken or over-permissive change.
  - **Decided for M4 (2026-10-28):** every rule needs a test (a rule that no test of its owner layer makes fire is an error, which also forces a changed rule to come with a changed or new test); `praksis layers update` refuses a result that gives a rule access no grant covers and shows the permission diff (an explicit flag accepts it); shadow mode is deferred to M5. A candidate for the verifier is the ruleset that `layers update` would produce, or a layer replaced by a directory or a git ref (so the AI's branch of the private layer can be checked before it is merged).
  - **M4 tasks:** (1) verifier core: `Verifier` with findings and a report, the validator's problems, `unused-need`, `effect-overstated`, `shadowed`, `empty`, and `praksis verify` (done); (2) permission requirements of a ruleset (per owner layer: capability and, per argument, the literal values or unbounded), the permission diff between two rulesets, coverage by the grants, and the gate in `layers update` (done); (3) ruleset tests (done): the `tests/<id>.toml` format in a layer, a runner that fires the real engine with recording capabilities, `praksis test`; (4) the coverage rule (every rule fired by a test of its owner layer) as a verifier check (done); (5) replay of the stored events through a candidate with recording capabilities and a behavioural diff against the current ruleset (`praksis verify --replay`) (done); (6) integration tests, including the done criterion (done): `DoneCriterionIT` pins a public mail layer and a private layer from real git repositories, then checks four branches of the private repository with `praksis verify --layer mine=@<branch>`: one with a filter on a field that mail does not have is rejected by the validator, one that files mail into a folder no grant names (valid and tested) is rejected for new access, one valid rule without a test is rejected by the coverage rule, and a rule within the grants with a test passes. The pins and the ruleset in use are unchanged by all of it.
- **M5, AI maintenance (the safety loop around an AI): done.** shadow mode, provenance, the approval tiers and a proposal workflow on the CLI. Done when a change made by an agent that passes the verifier runs in shadow mode and is promoted after the trial, and a change that needs approval waits for the user.
  - **Decided for M5 (2026-10-28):** Praksis does not call a model in M5. Any agent (for example Claude Code run by the user) works on a git branch of a layer, and Praksis verifies and approves what comes out; the branch, not the agent, is the interface. **Shadow mode comes first**, because it is independent of the AI and is the larger engine change. A built-in AI is the milestone M7.
  - **M5 tasks:** (1) shadow mode in the engine (done, see "Shadow mode (M5)" below): a rule in shadow mode is evaluated like any rule (filter, arguments, results as default values as in replay) but its capabilities are not called, its `stop` does not end the event for later rules, and what it would have done is recorded (table `shadow`, schema version 4); a rule is in shadow when its `(id, hash)` is not in the table of promoted rules, with the rules in use when the feature first starts adopted as promoted; `praksis shadow` shows per rule the trial start, the events seen and the calls it would have made, and the difference to what the live rules did for the same events; `praksis shadow promote <rule>` and `discard <rule>`; a trial period (a local setting, default 7 days, and a minimum number of events) after which the daemon reports that a rule is ready, never promotes by itself in the strict policy; (2) provenance (done, see "Provenance (M5)"): who wrote each rule and each change (human or AI, from the git author and a trailer such as `Praksis-Author: ai`), the reasoning and the verification result, recorded in the audit log and shown by `praksis effective`; (3) the approval tiers as a local setting (done, see "Approval tiers (M5)") (`policy.toml`, strict by default): always needs the user (widening grants, destructive or external effect class, edits to rules the user wrote), everything else that passes the verifier goes to shadow mode; (4) `ai_maintained` per layer in `praksis.toml` (done, see "AI-maintained layers (M5)") (default on for the user's own layers, off for upstream layers; for those a branch is prepared and the user submits it); (5) proposals (done, see "Proposals (M5)"): `praksis proposals` lists branches of AI-maintained layers, `proposals show <layer>@<branch>` runs the verifier report (checks, permission diff, behavioural diff by replay) and the tier decision, `proposals approve` merges the branch into the layer's pin and puts the changed rules into shadow mode, `proposals reject` records why; Praksis never pushes to a repository that is not the user's, and pushing always needs the user's action; (6) integration tests with real git repositories, including the done criterion above (done): `AiMaintenanceIT` runs the whole loop with a running daemon and the user\'s layer signed with an SSH key. An unsigned branch with a new rule is shown (tier SHADOW) and approved for its exact commit, the daemon restarted with the new pin observes the rule while the live rule keeps filing the mails, `praksis shadow` shows what it would have called next to what really happened, the user promotes it and the next mail goes where it says; then a branch that changes the user\'s own rule is shown as needing approval, and while it waits the daemon, the pin and the filing of mail are unchanged.
- **M6, JavaFX frontend:** a client of the local API for status, the effective view, the approval queue, commands and views (see the Frontend decision).
  - **Decided for M6:** the decisions under "Frontend and views" above (a generic renderer, no FXML descriptions, the daemon describes the UI and resolves views, views in layered TOML checked by the verifier). The order of the tasks below is the plan of 2026-10-29: the API first, because every client needs it, including a later web or mobile one.
  - **M6 tasks:** (1) the API for the engine screens (done, see "Screens API (M6)"): daemon requests for what the admin commands print without a daemon today (effective view with provenance, verify and the verdict, layer status, shadow, proposals), and a way to follow changes (polling at first, an event stream if polling is not enough) for status, the approval queue and new requests, so that a frontend can notify the user; (2) command triggers (done, see "Commands (M6)"): `trigger.kind = "command"` with a title and typed parameters in the rule, the loader, the validator and the verifier (a command is a rule that nothing but a person starts, so its calls need grants like any other), requests to list the commands and to run one with typed arguments, and the audit trail of who started it; (3) the view format (done, see "Views (M6)"): the TOML vocabulary (table, list, detail, form, button, text), loading views from layers with layering and the verifier checks (the data source must be a read-only capability, expressions must type-check, a `schema_version`), resolving a view in the daemon by running its query under the grants of the layer that owns the view and sending a resolved description, and the default presentation of data types in module descriptors; (4) the JavaFX shell: connects to the socket, shows the status, notifies on new approval requests, reconnects when the daemon restarts, runs on Linux first, and ships as its own jlink image so the headless daemon stays small; (5) the engine screens in JavaFX: effective view, approval queue (allow once, allow always, deny, replay), grants and credentials, audit log, shadow, proposals with the verifier report; (6) the generic renderer for commands (forms generated from the typed parameters) and views (the component catalog), and the message for a view with a newer schema than the frontend knows; (7) tests and the done criterion: the frontend answers an approval request and starts a command, a view from a layer is shown with data from a module, with UI tests on a headless JavaFX (TestFX with the Monitor platform) and the protocol tests against the real daemon.
  - **Open for M6 (settle at the start of the task they belong to):** how a module declares the default presentation of its data types (deferred to the M6b spike, see Views); whether the frontend ships in the image of the daemon or on its own (proposed: on its own, task 4); who may answer approvals when there is a GUI (today only the local socket answers, which stays true for a GUI; a GUI must never run on behalf of an AI agent, so answers need a person at the keyboard, to be looked at again with M7)
- **M6b, mail application (2026-10-29):** a basic mail program on top of the frontend, with sending. Done when a person reads mail, replies and sends it through the frontend, against a test IMAP and SMTP server, and the sent mail is in the Sent folder. It follows M6 tasks 1 to 6 (it needs the API, commands and views) and comes before the module extraction. The mail program is configuration, not code in the frontend: the modules provide the capabilities, `Praksis-Mail` provides the views and commands, and the frontend renders them. The risk to settle first is whether the generic renderer is enough for mail (a list of 50,000 messages, a message that must appear at once, typing in an editor), so the first task is a thin spike.
  - **Decided for M6b:** sending is part of the first version. Mail content is untrusted input everywhere: remote content is never loaded by default, scripts never run, attachments are never opened or run by Praksis, and a link is opened only by the person. Sending is an external effect, so it always needs a grant, and there is a limit on how many mails may be sent per hour so that a faulty rule or an AI cannot send a flood.
  - **M6b tasks:** (1) the spike: `mail.folders`, `mail.list` and `mail.get` in the IMAP module (and Maildir), and one view with the folder list, the message list and the message pane, to see whether the component catalog of M6 is enough or mail needs dedicated components; the result is recorded here before anything else is built; (2) reading: folders with unread counts, a message list with paging and sorting, a message with headers, text and HTML body and the list of attachments, attachment content as a separate capability with a size limit, search, flags (read, starred), and deleting (a move to Trash; removing for good is a destructive capability of its own); (3) a local cache of message headers in SQLite, kept in step with the server (UIDVALIDITY, new and removed mail), and IMAP IDLE so that lists change without polling, announced as events; (4) the SMTP module: `mail.send` (effect class external) with TLS and a credential binding, an append of the sent message to the Sent folder (`mail.append`), drafts, header injection refused, the limit per hour; (5) showing a message: plain text, HTML turned into a safe form (no scripts, remote content blocked until the person allows it for that message), attachments saved only by a person\'s action; (6) writing a message: a compose view with recipients (with completion from an address book module that starts with the addresses of received and sent mail), subject, body (plain text first), attachments, saving drafts, reply, reply all and forward with quoting, a signature; (7) daily use: keyboard shortcuts, drag and drop to move, conversation view (threading by References and In-Reply-To), a notification for new mail, several accounts and a screen to set up an account (including the credential binding, for which there is only the file today); (8) tests and the done criterion: against GreenMail with IMAP and SMTP, through the frontend on a headless JavaFX, a mail is read, answered and sent and is in Sent; a message with a remote image and a script shows neither; a rule that tries to send more than the limit is stopped.
  - **Open for M6b (settle at the start of the task they belong to):** whether the three-pane layout, selection state and virtual lists are components of the catalog or the mail program needs components of its own (task 1); how HTML is shown, with a sandboxed web view without JavaScript or by converting it to a restricted subset (task 5); who may send mail: only a command that a person starts, or also a rule that reacts to an event (an automatic reply), and then how a grant tells the two apart (task 4); the model for several accounts, since a module has one set of settings today (task 7); how much of the cache is kept for offline use (task 3).
- **Module extraction (after M6b, the mail application):** publish `capability-api` and `protocol` as versioned artifacts, define the module archive and `praksis modules install`, write the mail contract down in `Praksis-Modules-Mail` and move the IMAP, Maildir and SMTP modules there, and let the image and the integration tests use modules from outside the repository. See "Repositories". Before this, `Praksis-Desktop` is created at M6 task 4.
- **M7, full AI integration:** Praksis calls models itself, local first, and an AI becomes a first-class part of the system. The one rule that does not change: **a model has no rights of its own.** Its output is a proposal or a call that goes through the same capabilities, grants, audit log and approval tiers as everything else, and text that comes from outside (mail, web pages, transcripts) is untrusted input that can never widen what a model may do.
  - **Speech to text:** a `speech.transcribe` capability and a microphone or push-to-talk event source, with a local engine first (whisper.cpp or Vosk, so no audio leaves the machine) and a cloud engine as an option behind a credential binding; the transcript is an event (`speech.heard`) that rules and the command interface can react to; voice commands go through the same approval as typed ones. Text to speech for answers and read-aloud as the counterpart.
  - **Ruleset maintenance:** a built-in agent that proposes changes as branches (the M5 loop): rules mined from what the user does by hand ("you moved the last 12 mails from this sender to Lists"), fixes for failing tests after an upstream update, merging an upstream change into a private patch, tests written for untested rules, rules explained in plain language, unused or never-firing rules found from the run log, and permission requests explained in plain words next to the diff.
  - **General tasks:** a command interface in natural language ("move everything from the newsletter to Reading and tell me what you did") that is turned into capability calls or a one-off rule, shown to the user first when it changes anything; questions about the local data and history ("why was this mail moved?", "what did the rules do this week?") answered from the run log, audit log and stored events; multi-step jobs that run as a ruleset with a declared end.
  - **Model access as a module:** `ai.complete`, `ai.classify`, `ai.extract` and `ai.embed` as capabilities with an effect class that says data leaves the machine when a cloud model is used; local models first (a local server such as Ollama or llama.cpp), cloud models behind credential bindings; per-grant limits on what may be sent (a mail body may go to the local model and not to a cloud one), a token and cost budget, a log of every model call (what was sent, to whom, what came back), and no secrets in prompts.
  - **Suggestions for more:** mail and document summaries and a daily digest; classification of mail by content for rules that have no fixed header to match (a rule can call `ai.classify` and branch on the label, with the label checked against a list); extraction of dates, amounts and tasks from mail into the calendar or a task list; semantic search over the local storage with embeddings kept in the local database; drafts of replies that are never sent without the user; translation; OCR and ingestion of scanned documents and attachments; anomaly detection on the audit log ("this rule has called a capability it never used before"); an assistant for onboarding that sets up layers, modules and grants from a conversation; automatic test generation from replayed history; explanation of every approval request; accessibility through voice control and read-aloud; a "what changed and why" report for each update of an upstream layer.
  - **Safety work that belongs here:** prompt-injection defence (content from outside is passed to a model as data, with tool use turned off for the step that reads it, and a model that has read untrusted content cannot trigger a capability in the same step); evaluation sets so that a change of model or prompt is measured with the replay and test machinery before it is used; reproducibility (the model, prompt and settings of every AI-made change are recorded); an offline mode that works without any model.
- **M8, extensions:** schedules, more triggers and modules, then Windows and macOS.

An architecture document (components, module API, storage interface, event model, trust model) is written alongside M0 and M1.

## Name Suggestions

The concept: a general core, behaviour defined by rules, built from layered modules. The project started under the working title "SoftwareNG" ("next generation"). "Praksis" is the provisional name.

| Name | Idea |
|---|---|
| **Praxis** | Greek for "putting theory into action": rules become actions |
| **Loom** | Weaves modules and layered rulesets into what you actually need |
| **Canon** | The authoritative body of rules, and also a nod to "cascading" layers |
| **Tessera** | A single tile of a mosaic: many small modules forming one picture |
| **Concord** | Parts working together under shared agreements (rules) |
| **Keystone** | The central piece that makes the whole structure work |
| **Weft** | The crosswise threads that give the weave its pattern: rulesets over a fixed base of modules |

Decision: **Praksis**, the Danish variant of Praxis, is the provisional name. Loom was rejected because of the Atlassian product and Java's Project Loom. Praxis was rejected because it is crowded (PraxisLIVE, several trademarks, a pending PRAXIS OS filing). Trademark, domain and existing-project checks for "Praksis" (DKPTO, EUIPO, USPTO, praksis.* domains) are still open.
